# 多用户客户项目管理与统一排料设计

日期：2026-10-12。状态：用户已于当前会话回复“按此设计继续”，设计已确认。

## 目标与已确认范围

在现有窗序上增加注册登录，以及管理平台前端。管理平台与操作平台共用 FastAPI 后端和数据库。普通用户只能访问自己的业务数据；管理员能够查看全部用户的数据。业务层级为用户 → 客户 → 房屋项目 → 窗型，同一客户支持多个房屋项目。

保留现有窗型绘制、构件计算、型材排料、玻璃排版、导入导出、打印和手机操作。新增整项目统一排料：汇总各窗型乘以各自制作数量后的构件，再共同排料，不是相加各窗型独立计算的结果。

## 当前代码依据

- `backend/storage.py` 的 SQLite `projects` 表实际存放单个窗型 JSON，没有用户字段。
- `backend/main.py` 的存档、几何和排料接口均未认证。
- `backend/optimizer.py` 已按型材型号分组，并核对构件没有遗漏或重复。
- `backend/glass_optimizer.py` 支持贯通直切和有限库存，结果区分可行解与已证明的最优解。
- `src/store.ts` 使用所有访问者共享的浏览器草稿键；现有 `Project` 类型指的是单个窗型。
- 前端使用 Vue、Pinia、Vue Router、Axios、Element Plus，发布脚本统一构建 `src` 和 `public`。

## 实现方案选择

采用同仓库双前端入口、共享后端的方案。操作端与管理端分别拥有入口、路由与界面，共享类型、API 客户端和可复用组件。构建同时产出两个入口，后端提供静态文件。保留现有框架，不拆分成独立服务。

其他方案：把管理页直接加入操作端改动较小，但不如独立入口符合两平台的要求；拆分两个仓库和后端服务增加部署、版本与权限维护成本，本次不采用。

## 账号与权限

- 用户名与密码注册、登录、退出、查询当前账号；注册只能创建普通用户，不能提交管理员角色。
- 用户名规范化并建立唯一约束；密码使用带随机盐的可靠密码派生算法，不保存明文。
- 使用服务端会话与 HttpOnly Cookie；数据库只保存会话令牌摘要，支持过期和注销。写请求实施 CSRF 防护；生产 HTTPS 使用 Secure Cookie。
- 登录失败给予统一提示，并限制连续尝试；密码与会话令牌不进入业务日志。
- 管理员通过服务端命令创建，不使用固定默认密码，也不把第一个公开注册用户自动提升为管理员。
- 用户被禁用后已有会话立即失效。管理端可查看用户列表、启用或禁用普通用户；不开放管理员自我禁用。
- 客户、房屋、窗型、排料等接口在后端验证身份和所属用户；跨用户对象返回不存在，管理员跨用户查看使用明确的管理接口。
- 登录、注册、健康检查可匿名访问；业务计算、存档和数据查询要求登录。

## 数据模型

1. 用户：编号、规范化用户名、显示名称、密码摘要、角色、启用状态、创建时间。
2. 会话：令牌摘要、用户编号、过期时间、CSRF 信息。
3. 客户：编号、所属用户、姓名、电话、地址、备注、创建及更新时间。
4. 房屋项目：编号、所属用户、客户编号、名称、地址、户型描述、备注、统一型材原料与工艺配置、按玻璃材料分组的原板与排料配置。
5. 窗型存档：编号、所属用户、房屋项目编号、名称、楼层、房间／位置、玻璃材料标识、窗型 JSON、单窗原料和工艺配置、更新时间。

层级关联在事务中验证，不能将自己的窗型挂到他人的项目。数据归属从认证身份推导，不能信任客户端传入的用户编号。列表支持分页与名称搜索。客户和房屋存在下级数据时禁止直接删除，并说明原因；窗型删除需要前端确认。

兼容已有几何 `Project` 类型与版本 1 导入文件，以业务存档包装它，不把房屋项目伪装成几何模型。日期在数据库使用 UTC，界面按本地时间显示。

## 操作平台

登录后进入客户列表；选择客户查看房屋项目，再进入窗型列表。客户、项目、窗型支持新增、编辑和删除规则。窗型显示名称、位置、尺寸、数量，并提供编辑与单窗排料入口。

工作台显示客户和项目上下文，保存时保留归属。新增窗型可以快捷新增客户和房屋项目。保持现有绘图与尺寸编辑行为；表单继续使用 Element Plus 的 `ElForm` 校验与显式提交处理。

草稿按用户与窗型／项目上下文分别存放，保留保存目标。退出、账号切换和会话失效时清空内存中的窗型、历史、原料及结果，失效的异步响应不能写回新账号。切换窗型、离开工作台和启动整项目排料时提示未保存修改；整项目排料明确使用服务端已保存的窗型。

## 管理平台

提供独立管理端登录入口、总览、用户列表和用户数据浏览。管理员按用户查看客户、房屋项目和窗型详情，包括窗型结构、尺寸、数量及材料配置。业务数据默认只读；用户管理支持启用和禁用。普通用户即使直接访问管理页面或调用管理 API 也不能获取数据。

## 单窗与整项目排料

单窗保留现有两种排料及结果展示。项目详情新增整项目排料页，展示参与的全部已保存窗型、数量、楼层和房间，并分别配置型材和玻璃原料后计算。

### 统一求解与材料隔离

先对每个窗型独立完成几何校验及玻璃扣减，再展开制作数量，并加入稳定来源标识，之后调用抽取的公共排料内核。

- 型材按材料型号分组；型号代表可互换的原料，颜色、系列等不兼容材料必须使用不同型号。同型号跨窗型出现不同条宽时明确报错，不静默混排。
- 玻璃新增材料标识，规格、厚度、颜色或工艺不同使用不同标识；旧窗型默认归入“默认玻璃”，界面要求核对。每个材料组设置自己的原板、库存、刀缝和旋转规则，不跨组混排。
- 整项目采用项目级原料库存与工艺设置，不将各窗型库存相加，也不为每个窗型重复使用同一份库存。
- 每个输出构件保留窗型编号、名称、位置、制作实例序号和原始构件编号。内部唯一标识含窗型编号，避免多个窗型均有相同构件编号而碰撞。
- 汇总展示采购数量、成本、利用率和余料，同时保留材料分组明细、切割图和逐刀信息。页面、CSV、JSON、打印均保留来源，能够追溯到具体窗户。

### 容量与失败

整项目不能把现有单窗的 400 根型材／200 块玻璃限制直接当作项目容量。公共内核为较大构件集合提供确定性可行排料路径，小规模继续使用现有优化；在合理求解时限内返回完整可行方案，并如实标注没有证明全局最优。

任何路径必须遵守有限库存、锯缝、端部修整、玻璃材料隔离及贯通切割规则。启发式未找到方案时只能报告未找到可行方案，不能冒称数学不可行。资源上限通过实际压力测试确定并文档化；超限明确拒绝，绝不截断窗型或静默分批冒充统一排料。

空项目、无可排构件、玻璃扣减异常、缺料、库存不足、材料冲突均提供可定位到窗型／材料的中文信息。有一个窗型非法就阻止该次完整项目计算，不返回缺少部分窗型的成功结果。

## 存储迁移与发布

沿用 SQLite 并引入明确版本的事务迁移、外键、必要索引及忙等待配置，避免并发注册和存档覆盖。适用于单个服务实例和持久磁盘；不把本地 SQLite 描述成可用于无共享磁盘的多实例云部署。

迁移保留原 `projects` 数据及编号。旧无主窗型进入管理员可见的待归属区，由管理员明确分配给用户的房屋项目；不能自动交给第一个注册用户。提供迁移前备份与恢复说明；不在开发验证中修改真实 `data` 数据。

旧浏览器草稿不自动归属任意新账号，提供明确的本机草稿导入操作。原版本 1 文件仍可导入到选定项目并保存。更新本地启动和 veFaaS 构建，使操作端、管理端均包含于发布包，文档说明持久存储、HTTPS、管理员初始化与备份要求。

## 验收证据

1. 两个普通账号注册、登录、退出、重登；管理员从独立入口登录；会话过期和禁用后访问失败。
2. 使用真实 HTTP 测试覆盖全部客户、房屋、窗型、整项目排料读写接口的跨用户访问，以及普通用户访问管理接口。
3. 一个用户创建多个客户、每个客户多个项目、每个项目多个窗型；编辑、保存、重载后归属及材料配置不丢失。
4. 使用两种能够互补利用余料的窗型，验证整项目确实跨窗混排，并与独立排料结果比较；型材和玻璃分别覆盖。
5. 多窗数量展开、编号唯一、输出来源准确；材料不兼容时隔离；有限库存按项目共享；所有构件无遗漏和重复。
6. 覆盖超出原单窗规模的多窗项目，核对完整性、几何容量守恒与运行耗时；测试求解超时及库存不足。
7. 在临时数据库验证旧存档迁移、重复启动幂等、待归属分配和版本 1 文件导入，生产存档不参与测试。
8. 后端既有几何与排料回归、前端状态测试、类型检查、双入口构建；浏览器验证客户到窗型到项目排料完整流程、管理员浏览和手机布局。
9. 核对页面、CSV、JSON、打印的项目排料来源；账号切换后浏览器草稿与异步请求不会串号。

## 实施边界

不新增客户登录、员工共享账号体系、短信服务、付费订阅、报价或订单系统。管理员跨用户业务写入除旧数据归属分配外不在本次范围。不会自动推送或部署；交付包括源代码、迁移和管理员工具、中文说明及实际验证结果。
